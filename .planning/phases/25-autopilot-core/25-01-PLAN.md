    Key design decisions:
    - The loop is driven by a setInterval-based poller, NOT recursive async calls — avoids stack overflow on long runs
    - paused flag is checked at the TOP of each poll tick — guarantees loop stops at next safe point
    - watchPhase resolves a Promise when readState shows the current phase has advanced (completed_phases count increased)
    - Failure learning: before calling cb.recordFailure(), re-spawn with the GSD command plus a text note like `--retry "Phase ${phaseNum} failed. Previous attempt: ${reason}. Adjust approach."` via spawnGsdCommand args
    - GSD commands used: `/gsd:plan-phase` for planning, `/gsd:execute-phase` for execution. Pass phase number as arg.
    - Do NOT import anything that doesn't exist — only import CircuitBreaker, processSpawner, websocket, readers, db (all from Phase 24)

    Phase detection strategy:
    - readState() returns progress.completed_phases — compare against value at loop start
    - If completed_phases > startingPhases, the phase completed successfully
    - If the tmux session shows an error pattern in STATE.md status field containing 'failed' or 'error', treat as failure
    - Timeout: if a phase takes more than MAX_PHASE_MS (default 30 minutes), treat as failure
