**`readDockerDf()` implementation:**
```js
function readDockerDf() {
  try {
    const out = execSync("docker system df --format '{{json .}}'", { timeout: 5000 }).toString().trim();
    // docker system df --format '{{json .}}' outputs one JSON object per line
    const lines = out.split("\n").filter(Boolean);
    const entries = lines.map((line) => {
      const obj = JSON.parse(line);
      return {
        type: obj.Type,          // "Images", "Containers", "Local Volumes", "Build Cache"
        size: obj.Size,          // e.g. "13.8GB"
        reclaimable: obj.Reclaimable, // e.g. "7.2GB (52%)"
      };
    });
    return { entries, error: null };
  } catch {
    return { entries: [], error: "unavailable" };
  }
}
```

**`GET /docker-df` route — add after `GET /disk-detail`:**
```js
router.get("/docker-df", (_req, res) => {
  try {
    res.json(readDockerDf());
  } catch (e) {
    res.status(500).json({ error: e.message });
  }
});
```

The route is intentionally thin — all logic is in the helper for testability.

**Part A — `readOomStatus()` helper** (add after `readDockerDf()`):
```js
function readOomStatus() {
  try {
    const out = execSync("systemctl is-active earlyoom", { timeout: 3000 }).toString().trim();
    return { earlyoom: out === "active" ? "active" : "inactive" };
  } catch {
    // systemctl exits non-zero when inactive — catch means inactive
    return { earlyoom: "inactive" };
  }
}
```

```js
router.get("/oom-status", (_req, res) => {
```

**Part C — Update `CRON_WHITELIST["docker-prune"]`** (replace the existing entry, lines ~99-106):

Replace:
```js
"docker-prune": {
  schedule: "Sun 4:00 AM",
  logFile: "/var/log/docker-prune.log",
  cmd: "docker",
  args: ["system", "prune", "-f"],
  useSudo: true,
},
```

With:
```js
"docker-prune": {
  schedule: "Sun 4:00 AM",
  logFile: "/var/log/docker-prune.log",
  cmd: "bash",
  args: ["-c", "docker builder prune --keep-storage 2gb -f && docker image prune -f"],
  useSudo: false,
},
```

Rationale: `bash -c` allows two sequential commands. `useSudo: false` because the claude user is in the `docker` group and can run Docker commands directly. This avoids `sudo bash -c` complexity. The `run-cron` executor uses `cfg.useSudo` to prepend `sudo` — with `useSudo: false`, it runs `bash -c "..."` directly.

NOTE: Do NOT add `docker image prune -a` — only dangling images (no `-a` flag) per D-05.

**Part D — Update the actual crontab entry:**

```bash
(crontab -l 2>/dev/null | grep -v "docker-prune\|docker system prune"; echo "0 4 * * 0 bash -c 'docker builder prune --keep-storage 2gb -f && docker image prune -f' >> /var/log/docker-prune.log 2>&1") | crontab -
```
This removes any existing docker-prune line and adds the new two-step sequence at Sunday 4:00 AM.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server process → OS shell | execSync runs shell commands; output is parsed, not eval'd |
| client → /system/docker-df | read-only endpoint; no user input involved |
| run-cron executor → bash -c | CRON_WHITELIST is server-side constant; no user-controlled args reach bash -c |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-73-01 | Elevation of Privilege | CRON_WHITELIST docker-prune (bash -c) | mitigate | Command is a hardcoded string in server source — not user-supplied. `useSudo: false` means no sudo escalation. Docker socket access is via group membership only. |
| T-73-02 | Denial of Service | readDockerDf() execSync timeout | mitigate | `timeout: 5000` kills the child process after 5s; catch returns `{ entries: [], error: "unavailable" }` so the route responds 200, not hanging. |
| T-73-03 | Information Disclosure | GET /docker-df exposes disk usage | accept | Dashboard is single-user, cookie-auth gated at the Express middleware level (same gate as all /system/* routes). |
| T-73-04 | Tampering | crontab update command | accept | crontab write runs as the `claude` user (same as the server process) — no privilege escalation. The new entry is narrower than the previous `docker system prune -f`. |
</threat_model>
