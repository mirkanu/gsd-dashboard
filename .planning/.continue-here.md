## Conceptual Framing (agreed in conversation, not yet written to CONTEXT)

### Two Stack Categories

**General/Infrastructure stack** — provisioned at stage gates, same for every web project:
- Umami (analytics) — shared instance at umami.gsdlabs.dev, per-project WEBSITE_ID
- BetterStack (uptime) — global BETTERSTACK_API_KEY, per-project monitor
- R2 / Cloudflare (object storage/backups) — global R2_* keys, per-project bucket
- Sentry (error tracking) — global SENTRY_AUTH_TOKEN + SENTRY_ORG, per-project DSN

**Functional stack** — provisioned when a feature needs it, not every project uses all:
- PostgreSQL (DB) — shared root pw, per-project DB + password
- Resend (email) — per-project API key
- Cloudflare Tunnel (subdomain routing) — global CF keys, per-project ingress rule
- GitHub (repo) — global GITHUB_PAT, per-project repo

### Key Principles
- Maximise Claude Code configuration ability = minimum human setup requirement
- Prefer open source / self-hosted / free tiers
- Global API keys govern shared infrastructure; per-project keys/IDs govern project-specific resources

### What Needs Building
1. A single canonical `stackRegistry` (file or in-code object) listing every service with: category, global key names, per-project key names, custom domain (if any), provisioner module (if any), which stage/function gate triggers auto-provisioning
2. Sentry provisioner: create org project via API → store `{PROJECT}_SENTRY_DSN`
3. Umami provisioner: create website entry via API → store `{PROJECT}_UMAMI_WEBSITE_ID`
4. Update global CLAUDE.md to reference the registry as the source of truth for "what stack do we use"
5. Update stage gate at Beta→Launched to also include Sentry (and possibly Umami)
</decisions_made>
